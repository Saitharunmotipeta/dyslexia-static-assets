Relation ships between them :

1. facilities → departments
   Relationship: One-to-Many
   Description: One facility can contain multiple departments.
   Foreign Key:
   departments.facility_id → facilities.facility_id

2. patients → encounters
   Relationship: One-to-Many
   Description: One patient can have multiple encounters/insurance requests over time.
   Foreign Key:
   encounters.patient_id → patients.patient_id

3. facilities → encounters
   Relationship: One-to-Many
   Description: One facility can handle multiple encounters.
   Foreign Key:
   encounters.facility_id → facilities.facility_id

4. departments → encounters
   Relationship: One-to-Many
   Description: One department can manage multiple encounters.
   Foreign Key:
   encounters.department_id → departments.department_id

5. encounters → authorization_requests
   Relationship: One-to-One
   Description: Each encounter contains one authorization request.
   Foreign Key:
   authorization_requests.encounter_id → encounters.encounter_id

6. authorization_requests → authorization_procedures
   Relationship: One-to-Many
   Description: One authorization request can contain multiple procedures.
   Foreign Key:
   authorization_procedures.auth_request_id → authorization_requests.auth_request_id

7. encounters → encounter_history
   Relationship: One-to-Many
   Description: One encounter can have multiple status/activity history records.
   Foreign Key:
   encounter_history.encounter_id → encounters.encounter_id


Api endpoints;

1. GET /facilities
   Purpose:
   Fetch all available healthcare facilities for selection in the application.

2. GET /departments
   Purpose:
   Fetch all departments available under facilities.

3. GET /patients/{id}
   Purpose:
   Fetch patient details along with provider information and policy details.

4. POST /encounters
   Purpose:
   Create a new encounter for an insurance authorization request along with document verification details, condition type, and initial request status.

5. GET /encounters
   Purpose:
   Fetch all encounters for dashboard display and filtering based on request status or condition type.

6. GET /encounters/{id}
   Purpose:
   Fetch complete details of a specific encounter including patient details, verification details, and request status.

7. PATCH /encounters/{id}/status
   Purpose:
   Update encounter request status such as Approved, Denied, Pending, or Request More Information. This endpoint also creates an entry in encounter history.

8. POST /authorization-requests
   Purpose:
   Create and store authorization request details such as estimated amount, provider response, approval amount, and approval expiry information.

9. GET /authorization-requests/{id}
   Purpose:
   Fetch authorization request details for a specific encounter.

10. POST /authorization-procedures
    Purpose:
    Add procedure codes, procedure names, and expected amounts for an authorization request.

11. GET /encounter-history/{encounterId}
    Purpose:
    Fetch complete activity and status history of an encounter including status changes, timestamps, remarks, and updated user information.

12. GET /analytics/dashboard
    Purpose:
    Fetch analytics metrics such as total requests, approvals, denials, pending requests, delayed requests, and average turnaround time for dashboard visualization.
